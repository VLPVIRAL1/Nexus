# JSON import

Imports follow authorize → validate → stage → preview → commit. The server checks firm and assignment scope before locking the tax year. It limits byte size, nesting and record count; rejects unsafe object keys; validates UTF-8 and the canonical schema; and stores exact raw bytes, parsed data, a base revision and stable-ID child paths in PostgreSQL.

Absent fields do not change effective values. Null proposes a reviewed clear. Empty arrays do not delete records. Each change remains `use_imported`, `keep_existing` or `review_later`. Imported review/approval claims remain staged evidence and cannot create authoritative application records. Exact replays return the original batch while recording another attempt; a changed base revision records a stale rejection and forces a fresh preview.

Commit updates the canonical snapshot, tax-year revision, validation/calculation freshness, import result, attempt history and chained audit event in one transaction. The same transaction materializes taxpayer/spouse profiles, the filing profile, dependents, Schedule A, W-2 and nine supported 1099 families into the same internal records used by manual entry. Imported source IDs remain external identity only; changed source records create a new version and supersede the prior effective row. Corrected/void flags and an explicit external supersession reference preserve lineage without overwriting history.

The import preview overlays authoritative persisted taxpayer/spouse values before calculating differences, including for legacy returns whose canonical snapshot predates identity synchronization. After commit, users can edit imported identity/address data in **Taxpayer & spouse**, filing/dependent/Schedule A facts in **Return profile**, source boxes in **Typed source entry**, and Schedule C/E/F and allocations in their manual workspaces. Those edits invalidate stale calculations and outputs; identity and return-profile edits also update the canonical snapshot so a later import or rollback compares against the current value.

`client`, `source_documents`, `payments` and `review_points` have deliberately different authority boundaries. Client metadata cannot rename or reassign the selected firm client. Document references cannot upload original evidence bytes. Standalone payment metadata is not calculation input, and imported review claims cannot create authoritative review decisions. A nonempty value in any of those sections produces a visible warning and must be reconciled through its guarded manual workflow.

A compensating rollback restores the pre-import snapshot only when no later revision depends on the import, deactivates records introduced by that batch, restores eligible superseded rows, creates another tax-year revision and retains the original batch. Production use still requires encrypted storage and the production-data gate.

The versioned JSON Schema and matching Zod contract live in `schemas/2025` and `src/lib/canonical-schema.ts`. The application serves both an identifier-free blank template and a schema-valid synthetic review example. Complete JSON export uses that same importable contract, including filing status, dependent child rows and Schedule A; the example is test data, not tax advice or a filing-ready return.
